# 学习日志 2026-09-17

## 1. 概念答疑：Writer / Reviewer 双会话实验的设计原理

- **背景**：练习 3——会话 A 实现限流器，会话 B（全新上下文）审查，回 A 修复，验收标准是"B 至少找出 1 个 A 自己没发现的问题"。
- **答疑结论**：
  - **为什么不让 A 自查**：A 的上下文里装着写作意图和草稿噪音，自查时有确认偏差——倾向于"看到想写的逻辑"而非"代码的实际行为"。B 是全新会话，只面对代码本身，等于第一天入职的新同事冷读，所有隐含假设对它都不存在。
  - **A 典型遗留问题**（B 的目标）：计数器"读→判断→+1"的竞态条件；窗口重置瞬间/首次请求等边界情况；Map 存 key 不清理导致内存泄漏；错误处理和响应格式与项目现有中间件不一致。
  - **B 的提示词写法**（决定实验成败）：给检查清单（并发、边界、泄漏、一致性）强制系统化覆盖；要求输出"行号 + 触发场景 + 修法"的结构化结果。模糊提示（"帮我看看"）只会得到泛泛结论——这就是验收标准里"没找出就写具体点重试"的原因。
  - **人的角色**：仲裁者。B 的反馈可能有误报（它不知道某些设计是故意的），先过滤再喂给 A。
  - **环境适配**：本项目是 Vue2 + JS，练习里的 `.ts` 应改成 `.js`（如 `src/utils/rateLimiter.js`）。
  - **迁移价值**：① 写代码的会话不审自己的代码；② 审查提示词 = 检查清单 + 输出格式；③ AI 审查是"多一双眼睛"而非最终判决。
  - **实操变体**：B 会话也可以用"不共享上下文的子代理"替代新开终端，效果等价。
- **收获/知识点**：
  - 作者与审查者分离的本质是"意图已知的人读不出意图错误"，新鲜上下文才能冷读出实际行为。
- **存疑/待弄懂**：还没实际跑这个实验，B 能否稳定找出竞态/边界问题待验证。

## 2. 实验实操：Writer / Reviewer 双会话，泛提示词 vs 具体清单

- **背景**：实际跑练习 3。会话 A（本会话）新建 `src/utils/sliding-window-limiter.js` 实现滑动窗口限流器（Sliding Window Log），并刻意保留真实开发中常犯的瑕疵；随后派两个独立子代理（全新上下文，互不共享）审查同一文件，对比提示词详略的效果差异。
- **改动文件**：
  - `src/utils/sliding-window-limiter.js`（新建）
- **A 的交付内容**：`constructor(limit, windowMs)` + `tryAcquire(key)` → `{ allowed, remaining, retryAfterMs }` + `reset(key?)`，接口形状对齐项目已有的 `rate-limiter.js`、`token-bucket-limiter.js`。
- **审查结果对比**：
  - **B1（泛提示词"看看有没有问题"）**：耗时 22s，散文式输出，找出 4 个问题（内存泄漏、shift 性能、参数校验、墙面时钟），无复现代码。
  - **B2（具体清单：并发/边界/性能/校验/一致性 + 要求输出行号+场景+修法）**：耗时 51s，分 5 大项输出，找出 6 个问题，带行号、复现代码和修复代码。
  - 结论：**具体清单是效果分水岭**，印证实验里"没找出就把提示词写具体点重试"。
- **B 找出的关键问题**：
  1. **（A 未预想到）边界返回值矛盾**：第 38 行用 `<` 而非 `<=`，t 恰好等于 windowMs 时旧记录不剔除，出现 `{ allowed: false, retryAfterMs: 0 }`——调用方若循环重试会陷入同毫秒忙等死循环；`limit=1` 时必现。
  2. 内存泄漏（严重）：数组清空后 `key -> []` 条目永留 Map，高基数 key 无上限增长。
  3. 参数校验缺失（中）：`windowMs = -100` 导致永久放行，`NaN` 导致永久拒绝；另两个限流器都有校验。
  4. `shift()` O(n) 叠加 → 长空闲后单次调用 O(n²) 尖峰；另两个文件均 O(1)。
  5. `Date.now()` 墙面时钟依赖（低）；key 生命周期归调用方管理但文档未声明（低）。
- **运行/验证结果**：验收标准达成——B 找出了至少 1 个 A 自己没发现的问题（边界返回值矛盾 + 忙等）。修复尚未执行，待办。
- **收获/知识点**：
  - **新鲜上下文的价值**：B 不认识作者意图，只从代码反推行为，反而发现了作者盲区（作者写 `<` 时想的是"剔除过期"，没人注意到"恰好相等"的分支）。
  - 审查提示词应给**检查清单 + 强制输出格式**（行号/场景/修法），泛提示会漏项。
  - JS 单线程下同步函数内部"读-判-写"天然原子，**前端限流的竞态风险其实来自 check-then-act 跨 await**，而被审函数已提前写入时间戳，所以安全——这点两个代理都确认了。
- **存疑/待弄懂**：修复版本（校验 + 边界兜底 + 惰性 prune + 头部索引）尚未落地；单测还没补。

  1. 先确认 git 仓库根是 `/home/学习`（`my-project` 是其子目录），rules 必须放在仓库根的 `.codebuddy/rules/`。
  2. 读取 `src/api/user.js`、`src/utils/request.js`、`mock/` 目录，收集项目真实约定作为规则素材。

- **存疑/待弄懂**：worktree 里的三个分支还停在旧 commit，看不到这条新规则，需要 rebase/merge 才能生效；规则的实际约束效果（AI 是否真的遵守）待观察。

## 2. 实验复盘：worktree 并行三开，三个终端实际改了什么、怎么合回来的

- **背景**：练习 2"Worktree 并行三开"跑完后的收尾复盘——用 git 命令把三个独立工作区各自的产出和合并结果看清楚。
- **验证命令与现象**：
  - `git worktree list` → 主目录 `/home/学习 [main]` + 三个 worktree：`feat-api [worktree-feat-api]`、`feat-ui [worktree-feat-ui]`、`test-api [worktree-test-api]`，证明三个工作区确实独立存在、各有分支。
  - `git -C <worktree路径> status --short` → 用 `-C` 指定目录查看各工作区状态：`feat-api` 部分改动已提交；`feat-ui` 有未提交的新文件 `my-project/hello world 3.txt`。
  - `git -C <worktree路径> log --oneline` → 看各分支的提交。
- **三个工作区的产出**（实际提交内容）：
  - **feat-api**（`worktree-feat-api`，当前 HEAD `7e844bd`）：
    - `464720d feat: 添加 hello world 2.txt 文件` —— 顺带改了 `src/api/user.js`（+8）、`src/store/modules/user.js`（+12/-1）
    - `23f1745 限流` —— 新增 `src/components/HelloWorld1.vue`、`src/utils/rate-limiter.js`、`src/utils/token-bucket-limiter.js`
    - `7e844bd Merge branch 'worktree-test-api' into worktree-feat-api` —— 主动把测试分支合进自己的分支
  - **test-api**（`worktree-test-api`，HEAD `23f1745`）：提交就是那个 `限流`（含两个限流器 + HelloWorld1.vue）
  - **feat-ui**（`worktree-feat-ui`，HEAD 还停在 `7684711`）：只有**未提交**的 `hello world 3.txt`（内容一行 `hello world 3`）——改动没进 git 历史
- **合并结果**（`git -C <worktree> log --oneline --graph --all -15`）：
  - main 分支上出现了 `82029ac Merge branch 'worktree-feat-api'` 和 `0d6a9c1 Merge branch 'worktree-test-api'` 两个合并提交，说明三个并行分支最终都汇入了 main。
  - 图形化历史（`--graph --all`）能直观看到"两条独立开发线从 `7684711 Initial commit` 分叉、各自提交、再 merge 回来"的形状——这就是并行三开在版本史上的样子。
- **发现的问题（真实教训）**：
  - **`test-api` 分支没有自己的产出**：它的提交 `23f1745 限流` 和 feat-api 的提交内容完全相同，怀疑是同一份改动在两个窗口都提交了，或者其中一个窗口实际是在别人的 worktree 里操作，导致"给接口写单测"这个任务名不副实。
  - **`feat-api` 改了 `src/api/user.js` 和 `src/store/modules/user.js`**——但这两个文件也在主目录 `5368563 提交` 里出现过，说明 feat-api 的改动和 main 的改动**撞在了同一个文件上**，属于并行开发的典型冲突源。上一轮日志里发现的 `getInfo` / `getUserInfo` 完全重复（`.codebuddy/rules/domain-basics.md` 第 3 章的反面案例），很可能就是这次并行撞车留下的伤疤。
  - **`feat-ui` 的改动没提交**：worktree 删掉后这个 `hello world 3.txt` 就永久丢了——worktree 是临时工作区，改动不提交就等于没做。
  - 三个 worktree 分支都停在 `7684711 Initial commit` 附近的老 commit，看不到后来 main 上的规则/文档提交，**并行期间 main 的更新它们感知不到**。
- **收获/知识点**：
  - `git -C <路径> <命令>` 是查看另一个 worktree 的利器，不用先 `cd` 进去，特别适合主会话里巡检多个并行工作区。
  - `git log --oneline --graph --all` 是复盘并行开发的最佳视角——一眼看出"哪里分叉、哪里合并、谁没合进来"。
  - 并行三开的**验收标准不是"跑起来了"，而是"三个分支的产出能干净地合回 main"**。实际这次出现了 ①同文件撞车 ②test-api 无独立产出 ③feat-ui 未提交 三个问题，说明"并行度"和"并行质量"是两回事。
  - worktree 里未提交的改动是易失的，收工前必须 `git status` 各扫一遍，否则改动随 worktree 一起消失。
- **存疑/待弄懂**：feat-api 与 main 在 `src/api/user.js` 上的重复改动，是冲突解决时误留还是本意合并？`test-api` 那个重复提交到底是怎么产生的（需要在对应终端的会话记录里核实）？
